# Anifight — design

2026-10-16

## What this is

A MUGEN-compatible 2D fighting game engine that ships as a native Android app.
Version 1 is an **empty game**: the engine boots, runs its screen flow and draws
a full fight HUD, but there are no characters in it. Version 2 onwards adds
anime characters.

## Why MUGEN-compatible, and not "a fighting game"

The stated goal is to add famous anime characters later. There are two ways to
get there:

1. Build a bespoke fighting game and hand-author each character.
2. Build an engine that reads the file formats the fighting-game community has
   been authoring against for twenty years.

Option 2 is the whole point. MUGEN's ecosystem means a character is a folder of
`.def`/`.air`/`.cns`/`.cmd`/`.sff` files. Building a real loader means the
"add anime characters" step becomes a file copy rather than a modelling and
animation project per character. It also means the engine has a correct,
externally-specified target to test against instead of us inventing semantics.

So the engine is a compatibility project. When something is ambiguous we match
what MUGEN does, even where MUGEN's behaviour is odd.

## Goals for v1 (the "empty game")

- A native Android app, landscape, fullscreen, that starts straight into the game.
- Loads a real MUGEN-layout `data/` folder out of the APK.
- Parses `mugen.cfg`, `system.def`, `fight.def`, `select.def`, `system.sff`,
  `system.fnt`, `fight.sff`, `fight.fnt` and the inline `[Begin Action]` blocks
  inside the `.def` files.
- Screen flow: title → character select → (VS) → fight, with back navigation.
- Character select shows an **empty roster**: the correct grid, the correct cell
  art, a working cursor, and an explicit "no characters installed" state.
- The fight screen draws the complete HUD from `fight.def` — lifebars, power
  bars, portraits, names, round timer, win icons — over a stage background,
  with zero fighters.
- Renders at 60 Hz logic with device-independent scaling.
- Touch controls.

## Non-goals for v1

- Characters. No `.air`/`.cns`/`.cmd` loading, no state machine, no combat
  physics, no hit detection.
- Sound. The HUD declares `.snd` files; v1 parses and ignores them.
- Netplay, storyboards (`.def` storyboard files), demo/attract mode recording.
- Reading a user's own `mugen/` folder from device storage. v1 reads only
  what ships in the APK.

## Anti-goals

- **A lookalike.** If a real screenpack does not load, the project has failed
  even if it looks nice.
- **Shipping Elecbyte's assets.** The default screenpack that ships in the APK
  is generated by our own tool from our own art (`tools/screenpack/`). MUGEN's
  own `data/` folder is copyrighted and is not redistributed here.
- **A desktop-only engine that "will be ported later".** Android is the target,
  not an afterthought.

## The decisions, and why

**Native C++ core, Kotlin shell.** Kotlin is only the Activity, the
`GLSurfaceView` and lifecycle. Every piece of engine logic — format loaders,
screen flow, and later the match state machine and physics — is portable C++
with no Android API contact. `core/`, `gfx/` and `engine/` must not include any
`android/*` header; only `platform/` and `jni/` may. This is enforced by review,
and it is what will let the same engine build for desktop later to debug a
screenpack without an emulator.

**OpenGL ES 3.0.** Universal on Android since roughly 2013, and MUGEN draws
nothing but axis-aligned sprites, so a batched-quad renderer is the entire
graphics engine. Vulkan would buy nothing and cost compatibility.

**No third-party dependencies at all.** No AndroidX, no SDL, no stb. The app
links against the Android framework and its own C++ and nothing else. AndroidX
buys us nothing without an Android UI, and vendored C libraries would each need
auditing for the format work we are doing anyway.

**Aspect ratio: letterbox by default, not stretch.** Classic MUGEN stretches
its 320×240 screenpack across whatever surface it is given, which is why MUGEN
on a widescreen monitor looks horizontally squashed. On a 20:9 phone that is
much worse. `AspectMode::Fit` is the default; a game can opt back into classic
behaviour. This is our call, not MUGEN's, and it is the one place v1 knowingly
diverges from MUGEN's pixels.

**Three coordinate spaces, translated at load.** MUGEN 1.0 introduced the "game
coordinate space" (`mugen.cfg` `[Config] GameWidth/GameHeight`) and translates
assets authored for other spaces into it. A motif declares its own space in
`system.def` `[Info] localcoord`, a character in its own `.def`, a stage in its
own `[StageInfo]`. v1 must at minimum honour the motif's `localcoord`, because
the screenpack's every `pos` and `offset` is written in it.

**The empty game must still be enterable, or it cannot be tested.** MUGEN
itself refuses to start with an empty roster. We do not: the select screen shows
the empty grid, and the title menu exposes an explicitly-labelled engine test
entry that goes straight to the fight screen with placeholder fighters. This is
how the HUD, stage and camera get verified before any character exists, and how
we will know that "add a character" is the *only* remaining step.

## Known traps

Recorded here because each one costs an afternoon:

- `system.def` spells its sprite file key `spr`; `fight.def` spells its own
  `sff`. The same file format, two different key names.
- AIR `-1` duration means **hold this frame forever** ("no loop"), and a normal
  finite animation loops on its own. Other negative durations are zero-length.
- `[Begin Action]` blocks end at the next `[Begin Action]` header, not at a
  blank line.
- MUGEN's Y axis points up in stage/collision space but down in screen space.
- `select.def`'s random-cell marker is a bare `randomselect` line; there is no
  `randomselect/` syntax.
- MUGEN sprite RLE and `.fnt` versioning differ between v1 and v2 files, and v2
  adds LZ5. Both must be handled; most screenpacks in the wild are v1.

## How we will know it works

The bar is: **a real third-party screenpack, dropped into `assets/mugen/`,
loads and renders correctly.** Our own generated screenpack is a development
convenience and cannot be the only test, because a reader and a writer built
from the same mistaken belief will agree with each other and both be wrong.
The generator in `tools/screenpack/` is therefore written independently of the
C++ reader.
